The idea

Every app implements the same verbs. Nothing here knows about any specific app: this hub reads the apps/ directory and parses the single line of JSON that each app's status prints. Adding an app later means dropping a directory in — no change to the hub, no change to the engine.

Most apps write no scripts at all. They declare a kind and inherit every verb from it. A typical app is one app.conf and one compose.yml.

kindforthe app supplies
composedocker compose appsfiles/compose.yml, optionally files/env.template
systemdservices on the hostusually its own download.sh; declares unit=
containera bare docker run container that predates the catalogcontainer=, usually with adopted=1
scriptanything elseall verbs itself

Dispatch prefers apps/<name>/<verb>.sh when present, otherwise lib/kinds/<kind>.sh. Mix freely — netmon supplies only download.sh and inherits the other six.

The contract

verbmust do
downloadfetch and build; change nothing that runs
startbring it up
stopbring it down, keep data
updatefetch newer; restart only if it was already running
deleteremove it, keep data unless --purge
statusprint one line of JSON, change nothing
backup / restorerequired only when stateful=1

Exit codes

0 did it  ·  2 already in that state, nothing to do  ·  anything else, failed.

The 2 is what makes idempotency observable. start on a running app must return 2 — not re-run up -d and claim it did work.

status JSON

{"app":"paperless","kind":"compose","state":"running","installed":true,
 "containers":"3/3","health":"healthy","ports":8010}

state is one of absent, downloaded, stopped, running, degraded. Required keys: app, kind, state, installed.

Add an app

A complete app — install, start, stop, update, delete, status, backup and restore all work, and it appears on this dashboard:

apps/jellyfin/app.conf

kind="compose"
title="Jellyfin"
category="media"
desc="Movies and TV, with hardware transcoding if the box has a GPU."
ports="8096"
requires="docker"
stateful=1
detect="container:jellyfin"

apps/jellyfin/files/compose.yml

services:
  jellyfin:
    image: jellyfin/jellyfin:10.9.11     # pin it, do not track :latest
    container_name: jellyfin
    restart: unless-stopped
    ports: ["8096:8096"]
    volumes:
      - config:/config                    # named volumes, so backup works
      - ${MEDIA_DIR:-/srv/media}:/media:ro
volumes:
  config:

That is the whole app. Then, in the throwaway VM and never on the real server first:

cd testenv && make up && make sync
ssh homelab-test 'cd ~/homelab && ./homelab install jellyfin --apply'

Every app added so far has had at least one defect that only appeared on first run. Reading the docs is not testing.

detect probes are ANDed. Listing two alternative container names means the app can never read as fully installed — it will sit on partial forever.

Traps, in the order you will hit them

The volume is owned by root

Docker populates a fresh named volume from the image, so it arrives root-owned. An image running as a non-root PUID then cannot write: SQLite reports attempt to write a readonly database, and syncthing restart-loops without ever reaching a healthcheck. Fix it with a one-shot:

services:
  init-perms:
    image: alpine:3
    command: ["sh", "-c", "chown -R ${PUID:-1000}:${PGID:-1000} /config"]
    volumes: [config:/config]
    restart: "no"
  theapp:
    depends_on:
      init-perms: {condition: service_completed_successfully}

and declare oneshot="init-perms", or the exited init counts as a stopped service and the app reads degraded forever.

The healthcheck cannot run

Check the image has what you are calling. Many have no curl, only wget. Distroless images have no shell at all, so no Docker healthcheck works — declare health_url instead. Use 127.0.0.1, not localhost, which may resolve to ::1 while the app binds IPv4 only. And check what / returns: an app that redirects to a login page can send wget into a loop.

A missing device is a hard failure

Docker refuses to start a container whose devices: entry is absent, so never map /dev/dri unconditionally — it would break on every host without an Intel GPU. Leave it out of the compose file and write compose.override.yml from download.sh only when the hardware exists.

YAML folded scalars keep the newline

With >, a more-indented continuation line keeps its newline rather than folding to a space, which splits a shell command in half. Use a list: ["sh","-c","…"].

Pin the version of anything stateful

:latest means a routine update can carry a database across a major version unattended. Paperless built 3.1.0 from :latest while the server ran 2.20.13, and an export only imports into the version it came from.

Adopting what is already there

A server that has run for years already has services on it. Set adopted=1 and the catalog controls it without pretending it installed it:

  • download is a no-op that verifies the thing exists
  • delete refuses — removing something you did not install, by a route that never installed it, is how data disappears
  • update on an adopted container pulls a newer image but will not recreate it: docker does not record the original docker run arguments

Never point a compose app at containers created from a different compose file. The engine refuses, and the refusal is right: recreating them from your file hands a running database freshly generated credentials.

Safety

  • Nothing changes without --apply. Every command is a dry run by default.
  • --apply refuses unless /etc/homelab/allow-apply exists, so an --apply typed in the wrong terminal cannot change a machine that never opted in.
  • App scripts never call docker, systemctl or apt directly — they go through run. That is the whole dry-run mechanism, and it means an app cannot forget to honour it.
  • delete --purge on a stateful app asks you to type its name.
  • Before starting, the engine checks the ports are free, that no declared conflict is active, and that no foreign container already owns a name from the compose file.
  • restore refuses while the app is running: the database has already initialised a fresh cluster and holds those files open.

Moving an app to another machine

homelab backup   <app> <dir>          # on the old box
homelab download <app> --apply        # on the new one: images only
homelab restore  <app> <dir> --apply
homelab start    <app> --apply

The order matters and is enforced. install is download and start, so it is the wrong verb for a restore. Prefer this over an app's own exporter: a volume archive is byte-for-byte, whereas an exporter re-serialises through its model layer and can silently omit rows.

Testing

tests/conformance.sh <app>   # in the VM; drives the whole lifecycle
tests/checkjs.py             # this hub's JavaScript

13 assertions per app: every verb, idempotency, and that status emits exactly one line of valid JSON. It refuses to run outside the test VM, because it purges everything it touches.
